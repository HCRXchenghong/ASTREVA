# 日志留存与审计规范

> 目的：满足等保三级"安全审计"要求（覆盖每个用户、重要行为与安全事件可追溯，日志留存不少于 6 个月），并让值班人员知道**看什么、看哪里、多久看一次、异常怎么处置**。

## 1. 日志分类与存放位置

| 类别 | 内容 | 存储 | 保留 |
|---|---|---|---|
| 系统日志 | 控制台自身事件、官网访问明细、客服引擎审计事件、危险请求 | PostgreSQL `site_system_events` + `site_analytics_visits` | 事件 ≥180 天；访问明细 30 天（分层） |
| 内容审计 | 内容保存/发布/回滚、媒体增删、凭证变更 | `site_audit_events` | ≥180 天 |
| 客服审计 | 登录、接管、转接、结束、禁用客服、开放 API 调用 | 客服引擎审计事件（并入系统日志展示） | ≥180 天 |
| 运行日志 | 各服务 stdout/stderr、容器日志 | 宿主机/容器日志（journald / docker logs） | 建议 ≥30 天 + 关键告警归档 |
| 指标监控 | CPU/内存/磁盘/连接/构建/告警 | Prometheus + Grafana（`monitoring` profile） | 建议 90 天 |

## 2. 系统日志字段（每条记录）

`时间`、`来源`（系统事件 / 官网访问 / 客服引擎）、`等级`（info / warning / danger）、`分类`（visit / auth / api / security / admin / system / server）、`动作`、`中文描述`、`IP` 与 `IP 来源`（直连/代理）、`国家`、`方法+路径`、`状态码`、`User-Agent`（含浏览器/系统/设备解析）、`账号`、`请求 id`、`明细 JSON`（来源页、visitor_id、session_id 等）。

## 3. 触发 danger 的规则（当前实现）

1. 目录穿越（`..`、`%2e%2e`、双重编码）；
2. 敏感路径探测（`.env`、`.git`、`wp-admin`、`phpmyadmin`、`.aws`、`.ssh`、备份文件等）；
3. 系统文件探测（`/etc/passwd`、`/proc/self`）；
4. SQL 注入特征（`union select`、`sleep(`、`or 1=1`、`information_schema`）；
5. XSS 特征（`<script`、`onerror=`、`javascript:`）；
6. 扫描器特征（sqlmap / nikto / nmap / masscan / acunetix / nessus / w3af）；
7. 后台登录连续失败（≥10 次/15 分钟，IP+账号维度）→ 锁定并记 danger；
8. 2FA 连续失败（单挑战 ≥5 次）→ 作废挑战并记 danger；
9. 开放 API 无效/停用 Key 高频调用（配合限流）→ danger；
10. 非白名单来源的写请求（Origin 校验失败）→ warning。

## 4. 日常审计流程

| 频率 | 动作 | 关注点 |
|---|---|---|
| 每日 | 打开「系统日志」，等级筛选 `danger` | 是否有爆破/探测；同一 IP 是否反复出现 |
| 每日 | 看「数据看板」服务健康 | 客服引擎/对象存储/构建服务是否异常 |
| 每周 | 导出 CSV 归档，按 IP/动作聚合 | 趋势变化、异常地点或 UA |
| 每月 | 复核管理员与客服账号清单、权限、会话 | 离职/外包账号是否已禁用 |
| 每季度 | 备份恢复演练 + 保留策略核对 | 恢复可用、日志留存达标 |
| 每次发布 | 查看审计日志中本次发布记录 | 变更可追溯 |

## 5. 发现异常时的处置

1. **立即**：在「系统设置 → 客服账号」禁用可疑账号；必要时删除管理员账号（会即时撤销其全部会话）。
2. **阻断**：在 Caddy/云防火墙封禁来源 IP（应用层已在日志中标记）。
3. **取证**：在「系统日志」按该 IP/账号/时间窗导出 CSV，保留原始记录（系统日志不可篡改、只追加）。
4. **通报**：按你方安全事件流程上报，必要时向监管报告。
5. **复盘**：补充规则阈值、加固入口、更新本规范。

## 6. 日志保护要求

- 仅管理员可读（会话 + 2FA）；接口无删除单条记录的入口，只能按保留策略整体清理。
- 日志页支持"只看该 IP"与全文搜索，禁止把导出文件放在公网可访问目录（导出为浏览器下载）。
- 清理动作本身写审计（`system.events.purged`），记录清理范围与条数。
- 时间统一 UTC 入库、按站点时区展示，保证跨系统（客服引擎/控制台）时间可比对。

## 7. 与个人信息保护的关系

- 访问明细中的 **IP、User-Agent 属个人信息**：仅用于安全审计与统计，30 天后自动清理；对外展示与导出需限定在管理用途。
- 客户画像中的 IP：由客服在会话内查看（业务需要），画像可整体关闭；不得用于与客服无关的用途。
- Cookie 同意：分析类埋点仅在用户同意后采集，未同意不发送、不写本地标识。

## 8. 保留策略的配置与执行

- 默认策略：**安全事件与管理员操作 180 天**，**官网访问明细 30 天**（满足等保"审计记录留存不少于 6 个月"对安全事件的要求）。
- 可通过环境变量调整默认值：`ADMIN_LOG_EVENT_RETENTION_DAYS`（30–3650）、`ADMIN_LOG_VISIT_RETENTION_DAYS`（1–365）。
- 控制台「系统日志 → 保留策略清理」可临时指定天数执行一次清理；接口 `GET /site-admin-api/system/retention` 返回当前默认值，`POST /site-admin-api/system/events/purge` 接受 `{event_days, visit_days}`（超出范围会自动收敛）。
- 服务每天自动执行一次清理；清理动作写入审计（`system.events.purged`，含事件天数、访问天数与被清理条数），可追溯。
